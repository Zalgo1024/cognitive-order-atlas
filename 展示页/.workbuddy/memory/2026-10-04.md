## 第五轮 · 修复「顶栏放大镜点不开」（用户报障）

### 用户原话
「搜索点不开」+ 顶栏截图（能看到放大镜）。追问后确认：点放大镜应该**弹出一个搜索框搜内容**，且**只有放大镜坏**，其他交互正常。

### 根因（状态类只在部分断点下有样式）
`#srchBtn` 绑的 `openUI()` 只给 body 加 `srch-open` 类，而 **`srch-open` 的全部样式都在
`@media (max-width:1280px)` 里**。所以：
- **>1280px**：加了个没有任何样式的类 + 把光标塞进本来就常显的侧栏搜索框 → **顶栏按钮零反馈，用户判定"点不开"**（这就是用户的窗口宽度）
- 981–1280px：侧栏 64px 撑到 300px，有反应
- ≤980px：抽屉滑出，有反应

### 上一轮为什么没测出来（三条方法错误，必须记住）
1. 只在 **1100px / 375px** 测，恰好都是「能工作」的两档，**出问题的 >1280px 一档根本没测**。
2. 断言的是 `body.classList` 里有没有那个类 —— **加了个空类也判通过**。断言的不是用户看得见的变化。
3. 全程用 `eval` 里的 `element.click()`，**绕过命中测试**，天生查不出遮挡类问题。

### 改法
新增居中搜索面板 `.pal`（`z-index:200`，压过顶栏 140）：放大镜 / `/` / `⌘K` 一律唤出它。

案例 8 / 折叠区 17 = 101）+ 7 个可点快捷词，避免打开是空白。
`openUI` 与 `srch-open` 整块删除（CSS 9 行 + JS 4 处引用）。
匹配与渲染抽成共享引擎：`searchHits / hilite / countByKind / renderRows / scrollRowIntoView / goTo / isTyping`，

## 第六轮 · 页脚 CC 授权链接加浮层（用户点名）

### 需求
页脚 `CC BY-NC-SA 4.0` 外链要获得和正文术语一样的悬停/聚焦浮层，卡片里简单介绍这个协议。
用户定了：卡片详细度 = 标签 + 主行 + 说明；触屏保持直接跳转不变。

### 做法
- 新增 `TIPS` 表，**独立于 `TERMS`**。原因：`TERMS` 的键会被拼进 `Object.keys(TERMS).join('|')`
  作为正文术语正则（L4792），而 `CC BY-NC-SA 4.0` 里的 `.` 是正则元字符、整串又没转义 → 塞进去会变成通配匹配。
- `show()` 拆出 `resolve()`：按 `data-tip` / `data-tk` 分辨数据源，返回统一的 `{k, pl, d}`，两处触发源共用渲染。
- 三处 document 级委托选择器 `.term` → `.term,[data-tip]`（mouseover/mouseout/focusin 是连续一块，一次替换）。
- 页脚外链只加 `data-tip` 与 `aria-label`，`href/target/rel` 字符原样不动 → 点击行为零变化。
- 视觉暗示：`a[data-tip]` 虚线底边（沿用 `.term` 的语言），但 `cursor` 仍用链接默认，不用 `.term` 的 `help`。
- 可访问性：**不加** `aria-describedby`（浮层是全页共用一个元素、内容随触发源变，
  会出现「念到上一个术语残留文本」的错配；且说明较长，聚焦即全念是噪音）。
  沿用 `.term` 的既有思路——把要点塞进 `aria-label`。

### 顺带修的既有缺陷：浮层从不做纵向翻转
原 `place()` 只有 `top = r.bottom + scrollY + 9` —— **永远放下方**。页脚是文档最后一个元素，
链接下面只剩约 116px，而卡片 222px 高 → 卡片渲染到文档之外，**根本看不见**。
现改为：量真实尺寸 → 下方够就下方（与原行为逐像素一致）→ 否则翻上方 → 两边都不够时选空间大的一侧兜底。
顺带修好了页脚里术语卡片贴底的问题。

### 我自己引入又当场修掉的回归（值得记）
把 `place()` 横向右界从硬编码常量 `350` 改成实测宽度后，暴露出**循环依赖**：
`position:absolute` 且只设 `left` 时，元素宽度 = min(max-content, 可用宽度 = 容器宽 − left)，
而 `left` 又由量到的宽度算出来。**旧代码因为 `350 > 330` 恰好绕过了它**，改完在 375px 下
卡片被压成 **159px 宽**（细高文字柱）。修法：给 `.term-pop` 加 `width:max-content`，
宽度只由内容决定、与 `left` 无关，循环消失；`max-width` 改 `min(330px, calc(100vw - 24px))`。
> 教训：**改「位置↔尺寸」互相依赖的布局算法时，先把尺寸变成不依赖位置的量。**

### 测试方法学（又踩了一次）
`agent-browser` 的 `hover` 之后再插一个 `eval` 调用，悬停态会被重置（`.on` 变 false）；
但 `hover` 紧接着 `screenshot` 就能拍到卡片。所以：
**验证悬停要用「hover + 截图」或把断言和 `mouseover` 派发塞进同一个 eval**，
不要在中间插别的浏览器调用。另外翻转这类修复必须配前置断言「不翻转则必然溢出」，
再断实际未溢出，否则「碰巧没溢出」会伪装成通过。

7. `renderRows()` 加可选第 6 参 `headHTML`（分类视图要自定义表头 + 返回键）；不传则行为与原来完全一致。

### 本轮踩的两个坑（都是工具用法，值得记）

### 两处「看着像问题、其实是正常」的排查（都要记）
1. **GitHub Pages 抓取比本地少 5448 字节** → 一度以为是 Jekyll 处理坏了内容。
   实测：本地 5448 个 CRLF、远端 0 个，**换行归一化后逐字节一致**。
   数字巧合不是巧合：差 5448 字节 = 文件 5449 行 × 每行少一个 `\r`。
   → 纪律：**字节数不一致先数换行符**，别先怀疑内容被改。
2. **两次探测截图哈希完全相同** → 差点判成「假成功」。但两次探测**操作完全相同**
   （都开搜索面板、都搜「反噬」），渲染结果本就该一致。改成搜不同词后哈希分开
   （`c35be60057` vs `ccbb1410e8`），才证明是两次独立真实加载。
   → 纪律：**哈希相同要看「操作是否相同」**，不是一律判假。

### 我自己脚本的 bug（值得记）
`probe()` 函数内的命令**没有重定向到日志**，而外层脚本用 `> /dev/null 2>&1` 吞掉了 stdout
→ 断言 JSON 全部丢失，日志里只剩两个 `@@标记@@`。第一轮因此误判成「页面没打开」。
→ 纪律：**断言输出必须在函数调用处包 `{ ...; } >> "$LOG" 2>&1`**，不能只重定向外层的 echo。
